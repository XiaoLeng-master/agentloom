# 01 · 架构详解

> 本文描述目标架构；当前可运行范围以 README 状态表和 `internal/app` 的本地演示链路为准。Redis 可选用于演示 Trace 持久化；Kafka、Milvus、etcd 与自动优化发布尚未接入主请求链路。

> 配合 [`architecture.svg`](./architecture.svg) 阅读。本文回答"每一层为什么存在、它们怎么咬合"。

## 设计总纲

**一句话**：Agent 是决策层，后端基础设施是执行层与神经层。

四层 + 一横切：

| 面 | 职责 | 关键组件 |
|---|---|---|
| 控制面 | 对外入口与治理、任务拆解 | Gateway Filter Chain、Router/Orchestrator |
| 执行面 | 模型推理与工具执行 | Planner 池 / Executor 池 / Verifier 池 |
| 记忆面 | 状态与知识 | 会话状态(Redis)、向量库(Milvus)、多级缓存 |
| 观测面 | 自进化闭环 | Trace 采集 → Kafka → 评测 → 归因 → 优化 → 复测 → 热更新 |
| 后端底座（横切） | 可靠性基建 | 并发池、MQ、分表、幂等、缓存一致性 |

## 数据流：一次请求怎么走完

1. 用户请求经 **网关 Filter Chain**：API Key 认证 → Prompt 注入检测 → 全局/租户两级限流（令牌桶，目标架构；当前入口是 AccessPolicy、滑动窗口和并发信号量，见 [`docs/08-concurrency-quota.md`](08-concurrency-quota.md)）。
2. **Router** 按配置/关键词/模型意图路由到对应 Agent，做任务拆解与优先级调度。
3. 任务进入 **执行面** 三池：
   - Planner 池（贵模型，少而精）：拆任务、出执行计划；
   - Executor 池（平价模型，横向扩）：调工具、写回系统；
   - Verifier 池（规则 + 小模型）：校验结果、拦截敏感操作。
4. 执行过程中读写 **记忆面**：会话状态走 Redis + 本地两级、LaneLock 会话内串行；知识检索走 Milvus Top-K；热点结果走多级缓存。
5. 每一步产出 **Trace**（工具调用、LLM 输入输出、分支决策、延迟），异步写 Kafka。
6. 请求返回用户；Trace 进入 **自进化闭环**（见下）。

## 自进化闭环：Trace 怎么变成"会让 Agent 变好的数据"

```
① Trace 采集 ──异步──> ② Kafka 削峰 ──> ③ 批量评测(62+8 回归集)
                                              │
                                              ▼
              ⑦ etcd 热更新 <── ⑥ 复测门禁 <── ⑤ 优化任务(Prompt/切分 diff)
                     │                            │
                     └──────────> 闭环回流 ───────┘
                                  ▲
                                  │
                          ④ 失败归因(规则优先 + LLM 兜底)
```

- **① Trace 采集**：结构化轨迹，含工具结果 ID、延迟、token 计数；高频写不阻塞主链路。
- **② Kafka 削峰**：Trace 落 Kafka，可回放做回归；评测与主链路故障隔离。
- **③ 批量评测**：62 条正式回归集 + 8 条冒烟；4 类评测器（Prompt / RAG / Skill / Agent）；并发 worker + 信号量并发控制。
- **④ 失败归因**：失败轨迹聚类，归因到检索/Prompt/工具/模型哪一层；规则优先、LLM-as-Judge 兜底。
- **⑤ 优化任务**：产出可执行的 diff（改 Prompt、换分块策略、修工具描述）；版本化、可回滚。
- **⑥ 复测门禁**：同数据集同 case 幂等比较；目标 case 解决且无新回归才放行。
- **⑦ etcd 热更新**：优化结果通过 Watch + 引用计数灰度生效，零中断。

### 预测式归因（进阶）

每次优化提交声明一条预测："这次改分块策略，预计 HitRate@K +5~8 点"。
下一轮评测验证：
- 预测匹配 = 你对系统的理解对，归因可信；
- 预测证伪 = 你对系统的理解有偏差，比"分数涨了"更有信息量。

这把"分数涨跌 1 bit"升级为"分数方向 + 预测准确性 2 bit"，归因到"理解"而非运气。

## 后端底座（横切所有面）

| 技术点 | 落点 | 为什么不得不上 |
|---|---|---|
| 并发池 | Executor 池 worker pool + 信号量 + 两级配额 | 1 请求放大为 N 次下游调用，不控并发即雪崩 |
| MQ 削峰 | Trace 写入、评测任务、长任务全走 Kafka + DLQ | 评测批处理几分钟，同步接口必超时 |
| 分表 | Trace 按月分表 + 冷热分离，会话按 tenant 分片 | Trace 量大且只查近期；多租户隔离 |
| 幂等消费 | 评测任务幂等 key + DLQ | 重试不重复副作用 |
| 缓存一致性 | 知识更新事件 → 失效本地/Redis + 向量增量重建 | 文档改了缓存不失效 = Agent 答旧知识 |
| singleflight | 多级缓存重建互斥 | 防缓存 stampede |
