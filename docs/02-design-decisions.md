# 02 · 设计取舍

> 每一条都是"为什么这么做"，不是"我用了什么"。读代码的人问的是前者。

## 1. 为什么热更新用 Watch + 引用计数

纯 etcd Watch 会打断正在跑的请求：新配置一来，旧实例立刻失效，在跑的会话被切断。
解法：Watch 感知变更 → 创建新实例预热 → 旧实例引用计数归零后 drain 下线。
**收益**：运行中秒级切换、零中断。这是自进化闭环能"灰度生效"的前提——闭环的最后一公里。

## 2. 为什么评测规则优先、LLM-as-Judge 兜底

- 规则：可复现、可解释、零成本，覆盖工具选择/参数/检索命中/状态变更等确定性维度；
- Judge：只在规则无因时启用，避免评测器本身分数飘。
**收益**：两次评测可比，"分数涨了"可信。否则自进化闭环会被评测器噪声带偏。

## 3. 为什么按能力拆池而非按 Agent 拆

真正高并发的不是"思考"，是"调工具、写回系统"。
把稀缺的 LLM 推理（Planner，贵模型）与大量 I/O（Executor，平价模型）分离：
- 成本：贵模型实例少，不为高并发买单；
- 尾延迟：I/O 横向扩，不被推理阻塞；
- 治理：Verifier 独立池做门禁，敏感操作不靠"模型自觉"。

## 4. 为什么 Trace 走 Kafka 异步

Trace 是 Agent 的黑匣子，高频写入（每请求 N 条 span）。同步写库会阻塞会话主链路。
Kafka 的额外好处：可回放做回归——同一批 Trace 重跑评测，验证修复有效性。

## 5. 为什么每次优化带"预测"

分数涨跌只有 1 bit 信息，且无法归因。
预测 + 验证 = 2 bit：分数方向 + 预测准确性。
- 预测匹配：理解对，归因可信；
- 预测证伪：理解有偏差，记录为诊断信号，避免"分数涨了不知道为什么涨"。

## 6. 为什么自建 80 条公开评估集

- 公司数据不能开源（版权 + 隐私）；
- 私有数据不能开源，公开数据集可复现可审计，clone 下来就能打开 `datasets/rag_eval_80.json`；
- 80 条够覆盖检索命中、工具调用、多轮追问、安全边界四类，又不至于过拟合。
